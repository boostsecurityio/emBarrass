# eMudhra weak intermediate CA keys: facts and validator implications

Research snapshot: 2026-10-21

Scott Helme's article is the useful narrative starting point for this investigation; the technical and timeline claims below are traced to root-program, vendor, project, and library sources wherever available. [[Scott Helme, “Eight Bits of Trust”](https://scotthelme.co.uk/eight-bits-of-trust-emudhras-ca-keys-cracked-in-milliseconds/)]

## Executive finding

The incident affected eight ECDSA P-384 intermediate CA key pairs generated by eMudhra on 30 April 2025. Their private scalars were not merely weak in a general sense: every scalar was an integer below 256. Given a public point `Q`, the private scalar `d` is recovered by trying `d = 0..255` until `dG = Q`. This is enumeration of a tiny ECDSA private-key space, not RSA factoring or a break of P-384.

Six of the keys were TLS issuing-CA keys (DV, OV, and EV variants B and C); two were code-signing issuing-CA keys. Each key appeared in two certificate objects: one on an eMudhra trust path and one cross-signed by Sectigo's `AAA Certificate Services`. Therefore the incident comprises eight compromised keys but sixteen affected intermediate certificates. Mozilla's incident record is the canonical public chronology and certificate inventory. [[Mozilla Bug 2083449](https://bugzilla.mozilla.org/show_bug.cgi?id=2083449)]

This supports a local end-to-end validator: recover one of the six TLS private keys deterministically, use it to sign a short-lived leaf certificate for the requested host, and observe whether the wrapped program completes TLS verification and sends application data. The strongest practical identifier for all variants of an affected key is SHA-256 over the DER-encoded SubjectPublicKeyInfo (SPKI), not a whole-certificate fingerprint.

## Affected keys

These are SHA-256 hashes of DER SPKI, as used by the Go security patch. SPKI is the correct stable identifier because the direct and cross-signed certificates have different issuers, serials, signatures, and DER encodings while sharing the same public/private key pair. [[Go security patch](https://github.com/golang/go/commit/7f86f957633ee31a1c17a1eb8452ca7a3d9bc141)]

The scalar values above can be independently reproduced from the public certificates with the reporter's small Go program: parse the P-384 public key, compute `ScalarBaseMult` for each one-byte candidate, and compare coordinates. Published recovered PEM keys provide a cross-check, but a validator should derive and verify the key instead of trusting opaque embedded private-key bytes. [[Recovery code and artifacts](https://github.com/Fluepke/emudrahahahahaha)]

In Go terms, candidate zero is not a valid EC private key; candidates `1..255` suffice for these certificates. After recovery, the implementation should recompute the public point and assert the expected SPKI hash before serving anything. This turns source-data corruption or a programming error into a startup failure.

## Trust-store and verifier behavior

Revocation and distrust are application- and platform-dependent. A certificate being revoked does not make every offline or CLI verifier reject it.

- Mozilla pushed the directly trusted certificate objects to OneCRL, then shipped Firefox 158.0.1, ESR 115.43.1 and 153.5.1, and NSS 3.131.1 with the eMudhra ECC root removed. It followed with Firefox for Android 158.0.2 after some profiles failed to apply the new blocklist immediately at startup. A verifier with reliable, fail-closed revocation coverage can reject the intermediates without removing a root; Mozilla recommended intermediate blocks or root removal where that guarantee was absent. [[Mozilla Security Blog](https://blog.mozilla.org/security/2026/10/20/protecting-firefox-users-following-the-compromise-of-emudhra-intermediate-certificates/)] [[Mozilla dev-security-policy notice](https://groups.google.com/a/mozilla.org/g/dev-security-policy/c/0R3XLJL6FuE/)]
- Chrome blocked the eight SPKIs with CRLSet, covering both certificates for each key. Google also planned removal of the eMudhra ECC root. It reports that Certificate Transparency protected CT-enforcing Chrome clients: no leaf certificates chaining to these intermediates had appeared in public CT logs before the SPKI block. This does not imply the same protection for CLI TLS stacks, which generally do not enforce browser CT policy. [[Google Security Blog](https://blog.google/security/protecting-chrome-and-android-users-from-compromised-emudhra-intermediate-ca-certificates/)]
- Go added an explicit check for all eight SPKI hashes to both its pure-Go verifier and its Darwin/Windows platform-verifier paths. The fix is in Go 1.26.10 and 1.27.3 and is tracked as CVE-2026-111943. A statically linked executable retains the behavior of the Go toolchain used to build it; replacing the system Go installation does not alter an existing binary. `go version -m <binary>` can report embedded build metadata, but an end-to-end test remains authoritative. [[Go issue 82345](https://github.com/golang/go/issues/82345)] [[Go patch](https://github.com/golang/go/commit/7f86f957633ee31a1c17a1eb8452ca7a3d9bc141)] [[Go module/version metadata](https://go.dev/ref/mod#go-version-m)]
- OpenSSL only checks CRLs when the caller enables `X509_V_FLAG_CRL_CHECK` (and optionally `X509_V_FLAG_CRL_CHECK_ALL`) and supplies the relevant CRLs; it does not automatically fetch a CRL from a certificate's distribution point. Even `openssl s_client` continues after verification errors unless `-verify_return_error` is requested. Therefore “uses OpenSSL” alone is not a safety result. [[OpenSSL verification flags](https://docs.openssl.org/3.6/man3/X509_VERIFY_PARAM_set_flags/)] [[OpenSSL `s_client`](https://docs.openssl.org/master/man1/openssl-s_client/)]
- GnuTLS similarly makes credential loading, CRL loading, and peer-verification handling the application's responsibility; OCSP retrieval is not automatic merely because a certificate contains a responder URL. Therefore “uses GnuTLS” is also not a result without the application's configuration and error handling. [[GnuTLS certificate credentials](https://gnutls.org/manual/html_node/Certificate-credentials.html)] [[GnuTLS X.509 API](https://gnutls.org/manual/html_node/X509-certificate-API.html)]
- curl can use several TLS backends and trust stores. Its documentation characterizes OpenSSL/GnuTLS CRL use as manual while Schannel uses native automatic mechanisms. The validator must test the actual executable and build, not infer from a command name or library family. [[curl TLS feature comparison](https://curl.se/docs/ssl-compared.html)] [[curl certificate verification](https://curl.se/docs/sslcerts.html)]

## Safe local validator design

The following are engineering conclusions from the evidence above, not statements made by the incident participants.

### Interception boundary

For a portable, unprivileged Go wrapper, run a loopback-only HTTP `CONNECT` proxy on an ephemeral port and give only the child process standard proxy variables such as `HTTPS_PROXY`, `HTTP_PROXY`, and `ALL_PROXY`. This does not replace the child's CA bundle and therefore exercises its normal certificate verifier. curl and Git both document support for standard proxy configuration. [[libcurl environment variables](https://curl.se/libcurl/c/libcurl-env.html)] [[libcurl proxy option](https://curl.se/libcurl/c/CURLOPT_PROXY.html)] [[Git `http.proxy`](https://git-scm.com/docs/git-config#Documentation/git-config.txt-httpproxy)]

This must be described as proxy-mediated interception, not transparent network hijacking. A generic unprivileged wrapper cannot transparently redirect every child's sockets on every OS; doing so requires platform-specific facilities and often privilege. A program may ignore proxy variables, bypass the proxy through its own settings, use SSH, or fail before networking. In all such cases, “no observed traffic” is inconclusive rather than safe.

No upstream connection is required or desirable. The proxy can terminate TLS locally and return a small synthetic HTTP response. It should bind only to loopback and require a high-entropy per-run proxy-authorization token so unrelated local processes cannot create a false positive.

### Certificate construction

At startup:

1. Parse a known affected TLS intermediate certificate fixture.
2. Enumerate scalars `1..255`, derive each P-384 public point, and select the one matching the certificate public key.
3. Recompute and require the expected SHA-256(SPKI).
4. Generate an ephemeral leaf key and a short-lived leaf certificate containing the requested SNI/DNS name, `serverAuth` EKU, appropriate key usage, and authority key identifier.
5. Sign the leaf with the recovered intermediate key and serve the leaf plus the selected affected intermediate certificate.

Test the eMudhra-direct and Sectigo-cross-signed variants separately. A TLS Certificate message should not be treated as a bag containing arbitrary alternative paths; path construction differs between stores and verifiers. A `--chain=emsign|sectigo` option is predictable. Automatically executing an arbitrary user command twice is unsafe because commands can have side effects, so the default should perform one documented chain test and ask for an explicit second run for the alternative.

> **Superseded:** the default is now `--chain all`, which runs the command once per path (stopping early once one is accepted). A single-path default reported clients as protected when their store anchored only the other path; for example, Mozilla-derived stores trust `AAA Certificate Services` for e-mail only, so the Sectigo path alone misses clients that accept the direct path. `--chain emsign|sectigo` still limits a run to one path, so the command's side effects happen once.

### Proof and outcome states

TCP connection or `CONNECT` receipt does not demonstrate vulnerability. Even completion of the TLS handshake can precede an application's custom pinning or post-handshake policy. The strongest generic proof is that, after receiving the forged chain, the target sends an HTTP request (or other authenticated application bytes) over that TLS session.

Recommended state model:

| Classification | Evidence | Suggested exit |
|---|---|---:|
| **Vulnerable** | The child reached the proxy, accepted the forged chain, and sent an HTTP request/application data. Terminate the child process group immediately. | `1` |
| **Rejected / protected-likely** | The child reached the proxy, was offered the forged certificate, and then produced an explicit TLS certificate alert or recognizable certificate-verification failure. | `0` |
| **Inconclusive** | No proxy traffic, proxy bypass, non-HTTP protocol, pre-network command failure, ambiguous disconnect, or timeout. | `2` |
| **Harness error** | Fixture, key derivation, listener, certificate generation, or child supervision failed. | `2` (with a distinct machine-readable reason) |

The user-requested default can be a 30-second deadline. On proof, timeout, or interruption, terminate the entire child process group rather than only its immediate PID. Do not infer safety from the child's exit code alone.

If the command uses an option such as `curl -k` or `git -c http.sslVerify=false`, acceptance proves that verification was intentionally disabled; it does not specifically diagnose exposure to the eMudhra incident. Detect common explicit bypasses and label the result separately where feasible.

### Safety and privacy constraints

- Never forward intercepted traffic to the public destination.
- Do not log request bodies or security-sensitive headers such as `Authorization`, `Cookie`, or proxy credentials. Bound all request/header reads.
- Prefer a public, non-sensitive canary URL. A real repository URL can cause credentials to be transmitted to the loopback endpoint after TLS acceptance.
- Warn that killing `git clone` can leave a partial destination directory.
- Store only public incident certificates or their reproducible source references. Derive the already-public weak scalar at runtime and verify it cryptographically.
- Keep the code-signing keys in the incident inventory and blocklist tests, but do not use them to construct TLS server chains.

## Test corpus and acceptance criteria

The reporter publishes twelve TLS chains (six TLS keys times the two trust paths) and a JSON inventory. They are useful regression fixtures, but the Mozilla incident record and vendor repositories should remain the authority for identity and provenance. [[Reporter test site](https://emudhra.we-have-a-problem.com/)] [[Reporter source repository](https://github.com/galadran/we-have-a-problem.com)]

Minimum unit/integration checks for the future implementation:

- all eight certificate fixtures yield the expected scalar and SPKI hash;
- the six TLS keys can sign a leaf that verifies cryptographically beneath each corresponding fixture;
- altered fixtures, wrong hashes, scalar zero, and candidates outside the allowed set fail closed;
- an intentionally vulnerable local client reaches application-data proof;
- patched Go clients reject every affected SPKI, including both trust paths;
- a client that ignores proxy settings returns inconclusive, not protected;
- timeouts and proof-triggered termination reap the child process tree;
- logs and structured results never contain captured request secrets.

## Remaining uncertainty

The public root-cause analysis was preliminary as of this snapshot. Root-program emergency actions can also continue after publication, and OS trust stores are deployed asynchronously. The tool should therefore present its result as an observation about a specific executable, build, operating system, trust-store state, and tested chain at a particular time—not as a permanent verdict about a product family.
